# ออกแบบ: อัลกอริทึมวิเคราะห์เนื้อหาหน้าเว็บ (ชั้นที่ 4) + sandbox

> สถานะ: **ข้อเสนอ ยังไม่ได้ลงมือ** — เขียนไว้ให้ตกลงกันก่อนเขียนโค้ด
> เขียนเมื่อ 2026-07-27

---

## 1. ของที่มีอยู่ตอนนี้ทำอะไรได้/ไม่ได้

`analyzer/content_checker.py` ดึง HTML มาด้วย `requests` (จำกัด 512KB, timeout 5 วิ,
ไม่รัน JavaScript) แล้วหา 3 อย่าง:

| กฎที่มี | จับอะไร |
|---|---|
| `form_action_mismatch` | ฟอร์มมีช่องรหัสผ่าน แต่ `action` ส่งไปคนละโดเมน |
| `favicon_brand_mismatch` | favicon ดึงตรงจากโดเมนจริงของแบรนด์ |
| `content_brand_mismatch` | `<title>` พูดถึงแบรนด์ ทั้งที่โดเมนไม่ใช่ |

**ช่องโหว่ที่ใหญ่ที่สุด: ไม่รัน JavaScript** ชุดฟิชชิ่งสมัยใหม่ส่วนมากส่ง HTML เปล่า ๆ มา
แล้วค่อยวาดหน้าล็อกอินด้วย JS ตอนโหลด — ระบบตอนนี้จะเห็นหน้าว่าง ๆ แล้วสรุปว่า
"ไม่พบสิ่งผิดปกติ" ซึ่งแย่กว่าไม่ตรวจเลย เพราะให้ความมั่นใจผิด ๆ

ช่องโหว่รองลงมา:

- ฟอร์มที่ไม่มี `action` แต่ส่งข้อมูลด้วย `fetch()` ใน JS — มองไม่เห็นเลย
- ช่องรหัสผ่านที่ไม่ได้อยู่ใน `<form>` — กฎข้อ 1 ข้ามทันที
- ดูแบรนด์จาก `<title>` อย่างเดียว ไม่ได้ดูเนื้อความในหน้า
- ไม่รู้จักการอำพราง (`eval`, `atob`, `\x` escape, base64 ก้อนใหญ่)
- คะแนนเป็นการ **บวกกันตรง ๆ** สัญญาณอ่อน 3 อันที่ "รวมกันแล้วน่ากลัวมาก" จึงยังได้แค่เหลือง

---

## 2. หลักการที่จะไม่ทิ้ง

1. **อธิบายได้ ไม่ใช่กล่องดำ** — ทุกสัญญาณต้องบอกผู้ใช้ได้ว่า "เพราะอะไร"
   (ตามที่ `heuristics.py` ตั้งใจไว้ตั้งแต่แรก) ไม่ใช้โมเดล ML ที่ตอบไม่ได้ว่าเพราะอะไร
2. **"เช็กไม่ได้" ≠ "เสี่ยง"** — ดึงหน้าเว็บไม่ได้ต้องไม่เพิ่มคะแนน ไม่งั้นผลจะแกว่งตาม
   ความเสถียรของเน็ต (หลักการเดียวกับ `dns_fail` และ RDAP ที่เช็กไม่ได้)
3. **แยก "ดึง" ออกจาก "วิเคราะห์"** — ข้อนี้สำคัญที่สุดต่อการทำ sandbox ดูหัวข้อ 5

## 3. อัลกอริทึมที่เสนอ

แบ่งเป็น 5 ขั้น ขั้น A เป็นงานของ sandbox ที่เหลือเป็น pure function ทั้งหมด

### ขั้น A — ดึงหน้าเว็บ (งานของ sandbox)

คืน "page bundle" หน้าตาแบบนี้ ซึ่งเป็น**สัญญาเดียวที่ตัววิเคราะห์รู้จัก**:

```python
{
  "ok": True,
  "final_url": "https://...",       # หลัง JS redirect แล้ว
  "status": 200,
  "html": "<html>...",              # DOM หลังรัน JS เสร็จ (ไม่ใช่ HTML ดิบ)
  "raw_html": "<html>...",          # HTML ดิบก่อนรัน JS (ไว้เทียบว่าต่างกันแค่ไหน)
  "visible_text": "...",            # ข้อความที่คนเห็นจริง
  "scripts": ["...", "..."],        # เนื้อ <script> ทุกก้อน (inline + ที่โหลดมา)
  "resources": [{"url": "...", "type": "img|script|css|iframe"}],
  "forms": [...],                   # สรุปฟอร์มที่เจอ (รวมที่ JS สร้างทีหลัง)
  "network_posts": [{"url": "...", "cross_origin": True}],  # ปลายทางที่ JS ยิง POST
}
```

`network_posts` คือของใหม่ที่ได้จาก sandbox เท่านั้น และเป็น **สัญญาณที่แรงที่สุด**
ที่ระบบตอนนี้มองไม่เห็นเลย

### ขั้น B — ทำให้เป็นมาตรฐานก่อนเทียบ

ก่อนหาแบรนด์ในข้อความ ต้องล้างของที่ใช้หลอกตาออกก่อน ไม่งั้นเลี่ยงได้ด้วยการพิมพ์
`&#103;oogle` หรือแทรกอักขระความกว้างศูนย์:

1. คลาย HTML entity (`&#103;` → `g`)
2. normalize Unicode แบบ NFKC (ตัวอักษรเต็มความกว้าง → ปกติ)
3. ลบอักขระความกว้างศูนย์ (`​`, `‌`, `‍`, `﻿`)
4. ใช้ `normalize_glyphs()` ที่มีอยู่แล้วใน `heuristics.py` ซ้ำ (`g00gle` → `google`)

> ทำงานสองรอบเสมอ: หาแบรนด์ทั้งใน**ข้อความดิบ**และ**ข้อความที่ normalize แล้ว**
> ถ้าเจอเฉพาะอันหลัง แปลว่า "จงใจอำพราง" ซึ่งน่าสงสัยกว่าเจอตรง ๆ

### ขั้น C — สกัดคุณลักษณะ 4 กลุ่ม

**กลุ่ม 1 — การล้วงข้อมูล (สัญญาณแรงที่สุด)**

| id | เจออะไร | ระดับ |
|---|---|---|
| `form_action_mismatch` | (มีแล้ว) ฟอร์มรหัสผ่านส่งข้ามโดเมน | critical |
| `js_post_cross_origin` | JS ยิง POST ไปโดเมนอื่นจากหน้าที่มีช่องรหัสผ่าน | critical |
| `password_outside_form` | ช่องรหัสผ่านที่ไม่ได้อยู่ใน `<form>` (ต้องมี JS มาเก็บ) | high |
| `password_in_iframe` | ช่องรหัสผ่านอยู่ใน iframe ข้ามโดเมน | high |
| `form_action_ip` | ฟอร์มส่งไปยังเลข IP ตรง ๆ | high |

**กลุ่ม 2 — เลียนแบบแบรนด์**

| id | เจออะไร | ระดับ |
|---|---|---|
| `favicon_brand_mismatch` | (มีแล้ว) | medium |
| `content_brand_mismatch` | (มีแล้ว แต่ขยายจาก title → เนื้อความ + meta + alt) | medium |
| `logo_hotlink_brand` | รูปในหน้าโหลดตรงจากโดเมนแบรนด์ | medium |
| `brand_hidden_in_text` | เจอชื่อแบรนด์เฉพาะหลัง normalize (จงใจอำพราง) | high |

**กลุ่ม 3 — การอำพราง/หลบการตรวจ**

| id | เจออะไร | ระดับ |
|---|---|---|
| `js_obfuscated` | `eval(`, `atob(`, `String.fromCharCode`, `\x` escape หนาแน่นผิดปกติ | medium |
| `dom_differs_from_source` | DOM หลังรัน JS ต่างจาก HTML ดิบเกิน ~70% | medium |
| `instant_redirect` | meta refresh / `location.replace` ภายในไม่กี่ ms | medium |
| `devtools_blocked` | บล็อกคลิกขวา/ดักปุ่ม F12 | low |

**กลุ่ม 4 — คุณภาพหน้าเว็บ**
`no_favicon`, `single_page_no_links`, `html_too_small` — ระดับ low ทั้งกลุ่ม ใช้เป็นตัวประกอบเท่านั้น

### ขั้น D — ให้คะแนน (จุดที่เปลี่ยนจริง)

คงระบบ "สัญญาณ + คะแนน + เหตุผล" เดิมไว้ แต่**เพิ่มกฎการรวมสัญญาณ (combination rules)**

ปัญหาของการบวกตรง ๆ: หน้าเว็บที่ ① พูดถึงชื่อธนาคาร ② มีช่องรหัสผ่าน ③ โดเมนอายุ 3 วัน
— แต่ละอย่างเป็นแค่ medium/low พอบวกกันได้ 4 คะแนน = เหลือง ทั้งที่รวมกันแล้วมันคือ
**หน้าฟิชชิ่งเต็มรูปแบบ** ที่ควรเป็นแดงชัดเจน

```python
# เสนอเพิ่มใน analyzer/config.py
COMBO_RULES = [
    {
        "needs": {"content_brand_mismatch", "has_password_input"},
        "bonus": 4,
        "title": "หน้านี้ขอรหัสผ่านโดยอ้างชื่อแบรนด์ที่ไม่ใช่เจ้าของโดเมน",
    },
    {
        "needs": {"has_password_input", "domain_very_new"},
        "bonus": 3,
        "title": "หน้าขอรหัสผ่านบนโดเมนที่เพิ่งจดไม่กี่วัน",
    },
    {
        "needs": {"js_obfuscated", "has_password_input"},
        "bonus": 3,
        "title": "หน้าขอรหัสผ่านที่ซ่อนโค้ดการทำงานไว้",
    },
    {
        "needs": {"brand_hidden_in_text", "has_password_input"},
        "bonus": 5,
        "title": "จงใจซ่อนชื่อแบรนด์ไม่ให้ระบบตรวจเจอ พร้อมขอรหัสผ่าน",
    },
]
```

**กติกา:** combo ทำงานเฉพาะเมื่อสัญญาณที่ต้องการ "ถูกตรวจแล้วว่าเจอ" จริงเท่านั้น
ถ้าชั้นใดเช็กไม่ได้ (`checked=False`) ห้ามนับ — ไม่งั้นจะเดาแทนผู้ใช้

`has_password_input` เป็นข้อเท็จจริง (fact) ไม่ใช่สัญญาณเสี่ยง — ไม่ให้คะแนนในตัวเอง
เพราะเว็บล็อกอินจริงทุกเว็บก็มี แต่ใช้เป็นเงื่อนไขของ combo ได้

### ขั้น E — รายงานผล

เพิ่มใน `layer4` ของ JSON ที่ส่งกลับ: `content_checked`, `signals`, `combos_hit`,
และ `evidence` (ตัวอย่างข้อความ/URL ที่ทำให้เกิดสัญญาณ) เพื่อให้หน้าเว็บโชว์ได้ว่า
"เจอที่ตรงไหน" ไม่ใช่แค่บอกว่าเจอ

## 4. ทำไมต้องมี sandbox

ตอนนี้ระบบดึง HTML ที่ **มิจฉาชีพเป็นคนกำหนดเนื้อหา** เข้ามาแยกในโปรเซสเดียวกับที่ถือ
ฐานข้อมูลผู้ใช้และ `SECRET_KEY` ความเสี่ยงตอนนี้ยังต่ำเพราะ *ไม่รันโค้ดอะไรเลย* —
แค่ให้ BeautifulSoup อ่าน

แต่พอเราจะรัน JavaScript เพื่อแก้ช่องโหว่ใหญ่ที่สุด **ความเสี่ยงเปลี่ยนระดับทันที**
เพราะนั่นคือการเอาโค้ดของคนที่เราสงสัยว่าเป็นมิจฉาชีพมารันบนเซิร์ฟเวอร์ตัวเอง
สิ่งที่ต้องกันคือ:

- โค้ดในหน้าเว็บอ่านไฟล์/ตัวแปรสภาพแวดล้อมของเซิร์ฟเวอร์ (`.env`, `app.db`)
- ยิงเข้าเครือข่ายภายใน (SSRF ที่ผ่านมาทาง JS แทนที่จะเป็น redirect)
- กินซีพียู/แรมจนเครื่องล่ม (เช่น `while(true)`)
- ช่องโหว่ของ Chromium เอง (มีใหม่เรื่อย ๆ)

## 5. sandbox ที่เสนอ

### หลักการออกแบบสำคัญที่สุด: sandbox "ดึงอย่างเดียว" ไม่วิเคราะห์

```
                 ┌──────────────────────────────┐
  scanner.py ───▶│ sandbox (คอนเทนเนอร์ทิ้งได้)  │
                 │  Chromium headless           │
                 │  รัน JS ของหน้าเว็บจริง       │
                 └──────────────┬───────────────┘
                                │ page bundle (JSON ธรรมดา)
                                ▼
                 content_analyzer.py (pure function)
```

เหตุผล: ตัววิเคราะห์จะยัง **เทสต์ได้โดยไม่ต้องมีเน็ตและไม่ต้องมี sandbox** แค่ป้อน
page bundle ที่เขียนไว้ในไฟล์เทสต์ — คุณสมบัติเดียวกับที่ทำให้ `heuristics.py` และ
`qr_payload.py` เทสต์ง่ายอยู่ตอนนี้ ถ้าเอา sandbox ไปผูกกับตัววิเคราะห์เมื่อไหร่
คุณสมบัตินี้หายทันที

### ข้อกำหนดของคอนเทนเนอร์

| หัวข้อ | ค่าที่เสนอ |
|---|---|
| ฐาน | Playwright + Chromium headless |
| ผู้ใช้ | non-root, rootfs อ่านอย่างเดียว |
| เครือข่าย | ออกได้เฉพาะผ่าน proxy ที่บล็อก IP วง private/loopback/link-local ซ้ำอีกชั้น |
| เวลา | ตัดที่ 8 วินาที (รวมโหลด+รัน JS) |
| หน่วยความจำ | 256-512 MB |
| ซีพียู | 0.5 core |
| อายุ | หนึ่งหน้า = หนึ่ง context ที่ทิ้งทุกครั้ง (ไม่ใช้ profile ซ้ำ) |
| ของที่ปิด | ดาวน์โหลดไฟล์, ป๊อปอัป, กล้อง/ไมค์, notification, WebRTC |

**ห้ามพลาด:** การเช็ก IP ปลอดภัยที่ `destination_checker._resolve_safe_ips` ทำอยู่
**ต้องทำซ้ำอีกครั้งฝั่ง sandbox** เพราะ Chromium resolve DNS เองใหม่ (DNS rebinding
เปลี่ยนคำตอบระหว่างสองครั้งได้)

### จังหวะที่จะรัน

sandbox ช้ากว่า `requests` มาก (~3-8 วินาที เทียบกับ ~0.05 วินาที) จึง **ไม่ควรรันทุกครั้ง**
เสนอให้รันเมื่อเข้าเงื่อนไขเท่านั้น:

- ชั้น 1-3 ยังไม่ฟันธง **และ**
- (คะแนนอยู่ในช่วงก้ำกึ่ง 2-5 **หรือ** ดึงแบบเบา ๆ แล้วเจอช่องรหัสผ่าน)

แคชที่เพิ่งทำไป (`scan_cache.py`) ช่วยตรงนี้พอดี — หน้าเดียวกันไม่ต้องเข้า sandbox ซ้ำ

## 6. ลำดับที่ควรทำ

| ขั้น | ทำอะไร | ได้อะไร | ต้องมี sandbox ไหม |
|---|---|---|---|
| 1 | ขั้น B (normalize) + ขยาย `content_brand_mismatch` ไปทั้งหน้า | จับการอำพรางด้วย entity/unicode ได้ทันที | ไม่ |
| 2 | เพิ่มกฎกลุ่ม 1 ที่ดูจาก HTML ดิบได้ (`password_outside_form`, `form_action_ip`) | ปิดช่องที่ใหญ่รองลงมา | ไม่ |
| 3 | ขั้น D (combo rules) | หน้าฟิชชิ่งเต็มรูปแบบได้แดงแทนเหลือง | ไม่ |
| 4 | แยก `content_checker` เป็น fetcher + analyzer ตามสัญญา page bundle | เตรียมทางให้ sandbox เสียบเข้ามา | ไม่ |
| 5 | ทำ sandbox + `network_posts`, `dom_differs_from_source` | ปิดช่องโหว่ที่ใหญ่ที่สุด | ใช่ |

**ขั้น 1-4 ทำได้เลยโดยไม่ต้องรอ sandbox และได้ผลจริงทั้งหมด** — โดยเฉพาะขั้น 3 ที่แทบ
ไม่ต้องเขียนโค้ดใหม่เลย แค่เพิ่มตารางกฎ แต่เปลี่ยนผลลัพธ์ของหน้าฟิชชิ่งจริงได้เยอะที่สุด

ขั้น 5 ควรทำหลังเว็บขึ้น HTTPS และมี systemd แล้ว เพราะมันเพิ่มของที่ต้องดูแล
(คอนเทนเนอร์, Chromium, การอัปเดตความปลอดภัย) ไม่ควรทำพร้อมกับการ deploy ครั้งแรก
